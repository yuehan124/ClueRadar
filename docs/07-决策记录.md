## ADR-001 独立仓库 + 文档优先

- 状态：采纳
- 背景：原型最初放在 MediaCrawler 仓库的 `prototype/` 下，与上游教学项目耦合，
  且上游采用 NON-COMMERCIAL 许可，边界容易混淆。
- 决策：新建独立目录 `ClueRadar`，先落规范文档，再写实现。
- 理由：产品边界、技术栈、合规要求都与上游不同；独立后可以单独演进与授权。
- 代价：上游数据接入需要显式的适配层与跨仓库路径配置。
- 替代方案：继续放在上游仓库 —— 被否决，边界不清且污染上游。

## ADR-002 前端不复用现有 webui，选 Vue3 + Element Plus

- 状态：采纳
- 背景：上游自带 `webui/`，技术栈是 React + Radix + Tailwind。
- 决策：新建 Vue3 + Element Plus + Vite 前端。
- 理由：需求明确指定 Vue3/Element Plus；中后台表格、表单、抽屉组件更齐；
  团队协作成本低。
- 代价：已有 React 组件无法复用；需要重写。
- 替代方案：复用 webui —— 被否决，栈不匹配且改造量更大。

## ADR-003 后端选 FastAPI

- 状态：采纳
- 背景：需要 REST API、参数校验、异步调用 LLM、自动生成接口文档。
- 决策：Python 3.11 + FastAPI + Pydantic v2 + SQLAlchemy 2 + Uvicorn。
- 理由：
  - Pydantic 直接产出 OpenAPI，契约与代码同源；
  - 原生 async，适合 LLM 与采集编排；
  - 与上游 MediaCrawler 同为 Python，适配层可共用类型与工具；
  - 比 Django 轻，比 Flask 的类型与异步支持更完整。
- 代价：需要自己搭分层与迁移（我们用 Alembic + 明确的 api/service/repository 分层）。
- 替代方案：
  - Django：ORM/Admin 完整，但对纯 API 过重，异步生态弱。
  - Flask：需要额外拼校验与文档。
  - Node/NestJS：与采集侧语言不一致，无法复用上游代码。

## ADR-004 数据库选 SQLite（WAL）

- 状态：**已被 ADR-011 取代**（2026-10-20）
- 背景：单机原型，数据量预计 10 万级；本机虽有 PostgreSQL，但会增加部署与运维成本。
- 决策：SQLite + WAL + `busy_timeout`，通过 SQLAlchemy 异步访问。
- 理由：零运维、单文件备份、一条命令起服务；SQLAlchemy 让未来迁移 PG 的成本可控。
- 代价：
  - 单写者，写并发受限；
  - 需要显式约束长事务（禁止事务内调 LLM / 子进程）；
  - 调度必须单进程运行，否则定时任务重复执行。
- 替代方案：PostgreSQL —— 暂缓，数据量或并发上来后迁移。
- 迁移触发条件：写入 QPS 持续 > 20，或单表 > 100 万行，或需要多实例部署。
- **取代原因：需求方明确要求使用本机 PostgreSQL 实例，见 ADR-011。**

## ADR-005 部署在 `/radar` 子路径，history 模式

- 状态：采纳
- 背景：线上通过 `http://ip:port/radar` 访问，同机可能还有其他服务。
- 决策：Vite `base = '/radar/'`，路由 base 用 `import.meta.env.BASE_URL`，
  nginx 配置 SPA 回退与 API 代理。
- 理由：history 模式 URL 干净；base 单一来源避免漏改。
- 代价：
  - 必须配 `try_files`，否则刷新深链 404；
  - dev/preview 对无尾斜杠的 `/radar` 会 404，需要自定义中间件补 302；
  - 所有绝对资源路径必须经 Vite 处理。
- 替代方案：hash 模式 —— 零服务端配置，但 URL 带 `#`，不采用。
- 相关事实：nginx 对 `/radar/api/` 用 `proxy_pass .../api/` 剥掉 `/radar` 前缀。

## ADR-006 四层信号 + 加权评分，而非纯 LLM 打分

- 状态：采纳
- 背景：希望排序可解释、可调、成本可控。
- 决策：
  - 四层信号（噪声/意向/身份/阶段）负责过滤与特征提取；
  - 6 维加权公式负责打分（意向 30 / 阶段 25 / 身份 20 / 具体度 10 / 时效 10 / 热度 5）；
  - LLM 只负责语义判定（阶段、身份、摘要），不直接给总分。
- 理由：
  - 规则透明，销售能看懂"为什么 91 分"；
  - 权重可调，业务能自己调优；
  - LLM 只做它擅长的语义理解，避免"黑箱打分"和成本失控。
- 代价：
  - 规则需要持续维护词包；
  - 语义边界情况仍需 LLM 兜底，双通道要处理冲突。
- 替代方案：纯 LLM 打分 —— 不可解释、成本高、结果不稳定，不采用。

## ADR-007 继承脱敏边界，拒绝批量触达

- 状态：采纳（红线）
- 背景：上游为教学版，已移除创作者档案表，原始用户 ID 哈希为 `creator_hash`，
  昵称做掩码；许可证禁止商业使用。
- 决策：
  - 不实现去匿名化、反查、撞库；
  - 不抓取/存储联系方式；
  - 不生成私信群发内容；
  - 产品输出限定为"公开互动作业单"。
- 理由：合规与许可要求；也是产品差异化的基础（卖判断力，不卖骚扰能力）。
- 代价：无法直接联系用户，转化链更长，必须靠公开区的专业互动建立信任。
- 替代方案：无。此条不接受权衡。

## ADR-008 原型阶段用 Demo 数据与预置判定值

- 状态：采纳（有明确风险）
- 背景：先验证交互与信息结构，不等后端与模型。
- 决策：前端内置 24 条 Demo 线索，阶段/身份/摘要为预置值，评分由前端实时计算。
- 理由：能快速演示"降噪 + 分级 + 可解释 + 作业单"的完整闭环。
- 代价（必须说清）：
  - **预置判定值不能证明模型准确率**；
  - 前端评分与后端未来实现存在双份逻辑漂移风险。
- 缓解：V1 接入后，判定结果以服务端为准；前端只保留权重预览；
  建立人工标注集评估准确率。

## ADR-009 评分物化 + 异步重算

- 状态：采纳
- 背景：列表需要按分数排序，若每次请求实时计算全量，数据量上来后会变慢。
- 决策：`leads.score_total` / `score_grade` 落库；权重变更时异步批量重算。
- 理由：排序走索引，P95 可控；重算只发生在配置变更时。
- 代价：
  - 存在短暂"新旧分数并存"窗口；
  - 需要重算任务的状态与失败重试。
- 替代方案：实时计算 —— 数据量小的时候可行，但不具备扩展性。

## ADR-010 API 内部前缀 `/api/v1`，外部 `/radar/api/v1`

- 状态：采纳
- 背景：服务部署在子路径，且未来可能被其他前端复用。
- 决策：FastAPI 内部只认 `/api/v1`；nginx 负责剥掉 `/radar`。
- 理由：服务端不感知部署前缀，迁移或换域名时不用改代码。
- 代价：本地调试需要 Vite 代理或直接访问 8000 端口。
- 替代方案：服务端直接挂 `/radar/api` —— 与部署环境耦合，不采用。

## ADR-011 数据库改用本机 PostgreSQL 15

- 状态：采纳（取代 ADR-004）
- 背景：需求方明确要求使用本机已有的 PostgreSQL 15 实例
  （`D:\yuehan\PostgreSQL\15`，监听 `127.0.0.1:5432`）。
- 决策：
  - 数据库 PostgreSQL 15，独立库 `clueradar`，专用账号 `clueradar`；
  - 驱动 `asyncpg` + SQLAlchemy 2.x 异步；
  - 结构化字段用 `JSONB`，时间统一 `TIMESTAMPTZ`（库内 UTC，API 输出带偏移）；
  - 迁移用 Alembic，DDL 在事务中执行，失败可回滚；
  - 应用不使用 `postgres` 超级用户连接。
- 理由：
  - 实例已存在，无需新增部署成本；
  - 并发写、行锁、事务隔离、JSONB 查询、部分索引都强于 SQLite；
  - 支持多 worker（调度用 advisory lock 选主），不受单写者限制；
  - 后续做报表聚合与全文检索的余地更大。
- 代价：
  - 需要管理账号、备份与连接池；
  - 本地开发必须先建库建账号，环境准备步骤变多；
  - 时间类型从"本地时间字符串"改为 `TIMESTAMPTZ`，前后端需约定带偏移的 ISO 8601。
- 替代方案：SQLite —— 被需求方否决。
- 回滚策略：仍通过 SQLAlchemy 抽象数据访问，如确需回退，只改 `DATABASE_URL` 与迁移方言；
  但 `JSONB` / `TIMESTAMPTZ` 需要降级迁移，成本较高，故一次性确定。

## ADR-012 MediaCrawler 保持独立，只读接入，不修改上游工程

- 状态：采纳
- 背景：曾考虑让 MediaCrawler 改写 PostgreSQL，以减少跨仓库文件依赖；
  但 MediaCrawler 是独立上游项目，采用 NON-COMMERCIAL 许可，且已有脱敏改造，
  在 ClueRadar 的会话里修改它会污染上游、放大升级与合规成本。
- 决策：
  - 不修改 MediaCrawler 的任何工程文件与数据库；
  - 上游继续输出 SQLite（`../MediaCrawler/database/sqlite_tables.db`），
    ClueRadar 只读接入；
  - 平台字段差异全部收敛在 `backend/app/crawler/` 适配层；
  - 上游表结构、采集频率、脱敏策略均由 MediaCrawler 自己维护。
- 理由：
  - 保持上游可独立升级，避免 fork 漂移；
  - 合规边界清晰：ClueRadar 不参与采集实现；
  - 新项目只维护自己的 PostgreSQL 与业务代码。
- 代价：
  - 需要处理 SQLite 单写者与跨仓库路径；
  - 上游字段变更时适配层需跟进。
- 替代方案：
  - 改上游为 PostgreSQL —— 被否决，违反「不改上游」的边界；
  - 把上游表复制进业务库 —— 增加同步与合规风险，暂不采用。
- 回滚策略：无（本决策就是保持现状）；如未来上游官方支持 PostgreSQL，
  再评估只读接入方式。

## ADR-013 产品原型与正式前端分离

- 状态：采纳
- 背景：`prototype/` 最初是唯一前端，随着功能补齐，容易被当作生产前端继续改；
  需求方明确它只是产品原型。
- 决策：
  - `prototype/` 只作交互评审与设计参考，不接生产 API、不参与构建与部署；
  - 正式前端代码一律放 `frontend/`，构建与部署只认该目录；
  - 两者目录结构保持一致，迁移时按页面逐步替换数据源；
  - 演示数据必须以 SQL 为准（规划 `scripts/seed_demo.sql`），原型 mock 仅用于离线演示。
- 理由：
  - 边界清晰，避免 mock 数据、固定登录态进入生产；
  - 原型可以随时重做或删除，不影响线上；
  - 强制正式前端按 API 契约开发，减少"原型即上线"的返工。
- 代价：
  - 迁移期存在 UI 代码重复，需要人工保持视觉一致；
  - 原型与正式前端两套构建配置，需分别验证。
- 替代方案：
  - 直接把 `prototype/` 提升为正式前端 —— 被否决，mock 与生产逻辑耦合；
  - 保留两套但不定规则 —— 已被证明会混用。
- 回滚策略：若确需合并，把 `prototype/src` 迁入 `frontend/src`、删除 `prototype/`，
  并同步移除 mock 依赖；无数据迁移。
