# 08 · 合规与数据边界

> 本文是工程约束，不构成法律意见。正式商用前必须经法务评审。

## 1. 适用依据

| 依据 | 与本项目相关的要点 |
|---|---|
| MediaCrawler 许可证（NON-COMMERCIAL LEARNING LICENSE 1.1） | **禁止商业使用**；仅限学习研究 |
| 《个人信息保护法》 | 最小必要、目的限定；处理已公开个人信息应在合理范围内，个人明确拒绝的应停止 |
| 《数据安全法》 | 数据分类分级、安全保护义务 |
| 《网络安全法》 | 不得危害网络安全、不得非法获取数据 |
| 各平台服务条款与 robots | 不得绕过访问控制、不得大规模抓取、不得骚扰用户 |

**结论：当前形态只能用于学习研究与内部演示，不能对外商用。**
商用需满足至少一条：替换为合法授权的数据源，或取得上游明确授权，并通过法务评审。

## 2. 数据最小化

只保留"判断意向"所必需的信息：

| 保留 | 不保留 |
|---|---|
| 评论原文（判定依据） | 原始用户 ID |
| 匿名 `creator_hash`（同创作者归组） | 主页链接 |
| 掩码昵称（如「程***江」） | 头像 / 签名 / 性别 / IP 归属地 |
| 内容标题与公开链接 | 手机号 / 邮箱 / 微信号 |
| 公开点赞数、评论时间 | 设备标识 / Cookie / 精确定位 |

任何新增字段都要先回答：**没有它，判定还能不能做？** 不能做才允许加，并在此登记。

存储与访问控制：

- 数据库为本机 PostgreSQL 15（`127.0.0.1:5432`），不监听公网。
- 应用使用专用账号 `clueradar`，仅授予 `clueradar` / `clueradar_test` 的 `CONNECT` 与表级 CRUD，
  **不授予** `SUPERUSER` / `CREATEDB` / `CREATEROLE`。
- 已回收实例上其他数据库（`openease` 等）的 `PUBLIC` CONNECT，`clueradar` 无法连接；
  该收紧由 `scripts/harden_instance.sql` 固化，可重复执行。
- 备份文件同样包含数据，必须加密存放并限制访问，不得进入代码仓库。

## 3. 脱敏机制与局限

上游机制：

> ClueRadar **不修改** MediaCrawler 的工程文件与数据库，脱敏实现以上游为准；
> 本项目只读接入上游 SQLite 输出，所有平台差异收敛在适配层。

| 机制 | 实现 | 效果 |
|---|---|---|
| `creator_hash` | 原始用户 ID 经 sha256 后取前 16 位 | 无法直接反查，可用于同创作者分组 |
| `mask_nickname` | 昵称中间字符替换为 `***` | 降低直接识别风险 |
| 移除创作者档案表 | 无头像/签名/主页 | 无法拼出完整画像 |

**必须承认的局限**：

1. 哈希是**假名化**，不是绝对匿名。若同时掌握原始 ID 与哈希算法，仍可碰撞。
   因此不对外提供哈希，也不提供哈希查询接口。
2. 评论正文是用户自述，可能包含可识别信息（"我们厂在东莞"、"我是某某公司的采购"）。
   **脱敏层管不到正文**，这部分依赖：
   - 用途限定（只用于意向判断，不做人肉搜索）；
   - 访问控制（仅授权销售可见）；
   - 不外传、不导出、不二次加工成画像。
3. 公开不等于可任意使用。个人明确拒绝后应停止处理。

## 4. 红线清单（不可配置、不可协商）

| # | 红线 | 说明 |
|---|---|---|
| R1 | 不去匿名化 | 不反查、不撞库、不跨平台合并身份 |
| R2 | 不抓取联系方式 | 手机号、邮箱、微信、QQ 一律不采集不存储 |
| R3 | 不私信群发 | 不生成私信话术，不提供批量触达能力 |
| R4 | 不自动化批量互动 | 不写自动评论/点赞/关注脚本 |
| R5 | 不绕过平台风控 | 不破解验证码、不伪造设备、不规避限流 |
| R6 | 不出售/共享数据 | 不提供数据导出给第三方 |
| R7 | 不商用（当前许可） | 未经授权不得用于商业目的 |
| R8 | 不采集敏感个人信息 | 不含未成年人、健康、金融账户、行踪等 |
| R9 | 不把公开互动变成骚扰 | 同一用户 24 小时内最多一次公开互动 |

> 代码评审时，任何触碰 R1–R9 的 PR 直接拒绝，不论需求方如何要求。

## 5. 允许的互动方式

产品输出的作业单只允许以下动作，由**人工**在平台内执行：

| 允许 | 说明 |
|---|---|
| 公开评论 / 公开回答 | 在对方提问的公开内容下回复 |
| 提供公开资料 | 选型清单、评估表、公开案例 |
| 引导至公开渠道 | 平台内公开主页、公开的官方账号 |
| 记录跟进状态 | 在系统内记录，不对外 |

| 不允许 | 说明 |
|---|---|
| 私信对方 | 即使平台提供私信能力 |
| 索要手机号/微信 | 包括"方便留个联系方式吗" |
| 冒充客户/同行 | 不制造虚假身份 |
| 刷量/诱导互动 | 不买赞、不控评 |

## 6. 人工在环

- **所有对外动作必须由人执行**，系统只给建议，不自动发送。
- 作业单必须展示注意事项，且不可被配置隐藏。
- 销售在公开区互动前，需自行判断内容是否涉及敏感话题。

## 7. 审计与可追溯

| 项 | 要求 |
|---|---|
| 操作日志 | `audit_logs` 记录状态变更、设置修改、词包增删 |
| 日志内容 | 操作人、动作、目标、变更前后值、IP、时间 |
| 留存 | 180 天 |
| 访问控制 | 仅管理员可查审计日志 |
| 数据来源 | 每条线索可回溯到平台 + `comment_id`，便于下架 |

## 8. 权利人请求处理（下架机制）

即使已脱敏，仍可能有人要求删除其内容。流程：

1. 接收渠道：公开邮箱 / 平台内公开留言（不要求对方提供身份证明以外的信息）。
2. 定位方式：按 `platform + comment_id` 或评论原文精确匹配。
3. 处理动作：删除 `leads` 及其 `lead_signals` / `lead_activities`（级联），
   并在 `audit_logs` 记录下架原因（不保留原文）。
4. 时效：收到请求后 7 个工作日内完成。
5. 防复发：将对应 `comment_id` 加入排除表，后续采集跳过。

> 排除表只存 `platform + comment_id`，不存任何用户标识。

## 9. 数据保留

| 数据 | 期限 | 到期动作 |
|---|---|---|
| 线索与信号 | 业务存续期 | 定期清理失效且长期无跟进的线索（建议 12 个月） |
| 操作审计 | 180 天 | 归档或删除 |
| 采集执行记录 | 90 天 | 删除 |
| 上游原始库 | 建议 90 天 | 由 MediaCrawler 侧清理 |
